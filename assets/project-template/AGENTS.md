# 数学建模竞赛项目规则

## 总体约定

- 对数学建模竞赛题目、论文研究、方案设计、代码实现、检验、论文提纲和交接，使用 `$math-modeling-competition`。
- 开始任何实质工作前，读取 `PROJECT_STATUS.md`、`problem/`、`model/PLAN_STATUS.txt` 和 `HANDOFF.md`。
- 正式比赛采用“一个总控任务/对话 + 六个长期专业任务/对话”；`.codex/agents/` 是六个专业角色的持久职责合同，不把正式角色工作交给一次性同角色子 Agent。总控负责派单、跨任务路由、合并结论、处理冲突和执行质量门。
- 所有重要知识必须写入项目文件，不把聊天上下文视为持久资料库。
- 不伪造论文、DOI、数据来源、实验结果、检验状态或论文结论。

## 多对话协作

- 七个任务必须从同一个本地 Codex 项目主目录启动，使用共享目录而不是相互隔离的 worktree。各任务共享文件但不共享聊天记录，跨任务消息仅用于唤醒和指路；当前客户端不支持跨任务消息时，由用户人工转发 dispatch_id 与路径，不能因此省略落盘派单。
- 总控按 `coordination/README.md` 初始化、命名并登记任务；每个 logical_role 同时最多一个 `ACTIVE` 任务。丢失或重建时旧任务标为 `RETIRED`，新任务增加 generation。
- 正式工作必须先写 `coordination/dispatches/` 派单并登记 `coordination/dispatch-log.csv`，再向对应长期任务发送消息。专业任务只执行与自身 role、generation、thread_id、mode 和输入哈希匹配的一个活动派单。
- 专业任务完成后写 `coordination/receipts/` 回执。没有回执、输出路径和可核验文件时，总控不得把聊天中的“完成”合并为项目事实。
- 写入范围按 `coordination/path-ownership.csv` 独占授权；两个活动派单不得使用同一 `exclusive_scope_id`。实施者与验证者的 G2-B 可并行，但只能分别写自己的 review 与合成测试。
- `PROJECT_STATUS.md`、`HANDOFF.md`、`coordination/CONTROL-BOARD.md`、线程注册、派单总表、任务追踪总状态和 G2-C 用户批准只由总控更新。专业角色在回执中提出建议，不直接把质量门改为 `PASS`。
- 总控不能委派用户批准，也不能代签实施者/验证者；`release_packager` 长期任务在没有用户当前明确打包命令时保持空闲。

## 专业角色

- `literature_researcher`：领域与算法文献检索、合法全文下载、教材章节取证、证据矩阵与算法覆盖审计。
- `model_architect`：任务分解、算法证据需求、Tier 方案、受保护科学决策、数据预处理契约、候选比较、最终方案和预注册检验。
- `model_implementer`：冻结前以 `PREFREEZE_READINESS` 审查可实现性；冻结后以 `G3_EXECUTION` 实现各 Tier、运行实验并登记全部论文产物。
- `model_verifier`：冻结前以独立身份挑战方案可检验性；G4 再以独立证据复现、执行灵敏度/稳健性/消融和声明审计，二者不得混同。
- `paper_outline_writer`：只依据已验证结果编写论文写作大纲和声明—证据映射，不创造结果。
- `release_packager`：仅在用户明确下令时执行快照或正式发布。

## 数据、证据与产物

- 将 `data/raw/` 视为只读；清洗和变换后的数据写入 `data/processed/`。
- 每个原始数据文件登记来源、许可、字段、单位、时间范围和 SHA-256；无官方数据时也要明确记录。
- 对外部论文记录可验证的题名、作者、年份、DOI 或正式链接，并区分原文事实、Agent 归纳和迁移判断。
- 本地教材只有在来源与使用权限可说明、版本/章节/页码可定位时才能进入正式证据链；来源不明时登记 `ACCESS_UNVERIFIED`，不得摘录、引用或随包分发。
- 正式数值、表格和图必须登记到 `outputs/artifact-manifest.csv`，并可追溯到输入数据、脚本、命令和运行编号。
- 论文全文和教材只在授权范围内使用。默认打包不包含 `research/library/papers/` 和 `research/library/books/` 的全文。

## 质量门

按顺序执行：G0 赛制、题目与数据；G1 文献证据；G2 预处理与模型冻结；G3 实现与结果；G4 独立检验；G5 论文提纲交接；完整论文形成后执行 G5.5 晚期 AI 辅助自查；G6 用户命令触发的打包。G5.5 是 G5 的补充检查，不新增或篡改官方质量门编号。

- 各门状态统一使用 `NOT_STARTED / IN_PROGRESS / BLOCKED / PASS`；只有证据文件非占位且阻塞项为零时才可记 `PASS`。
- 通过每一门后由总控核验专业任务回执和实际产物，再同步更新 `PROJECT_STATUS.md`、`HANDOFF.md` 与 `coordination/CONTROL-BOARD.md`。
- 未完成 G1，不得声称方案具有充分文献支持。
- G1 包含“基础检索—候选算法需求—定向方法检索—证据回审”回路；G2 新增算法或重要变体时必须重新打开定向 G1，旧证据标记 `STALE`。
- 每个最终核心算法组件必须映射到可核验的理论、教材/专著、相近任务应用和比较/局限证据；证据缺口、版本不一致或只能凭摘要核对理论细节时不得冻结。
- G2 分为 G2-A 方案设计、G2-B 实施者/验证者冻结前联合可实现性审查、G2-C 用户审批与同步冻结。G2-B 只允许纸面和合成小例，不读取正式结果、不运行真实模型、不生成正式产物；`model/implementation-readiness.md` 必须为 `READY_FOR_USER_REVIEW` 且双签收后才能进入 G2-C。
- 每题至少有 Tier 0 简单基线与 Tier 1 竞赛主力模型；Tier 2 可明确不适用，仅在预注册的增益、稳定性、校准和预算门通过后升级。冻结回退顺序为 Tier 2 → Tier 1 → Tier 0；Tier 0 仍能完整回答题目时允许限制声明后交付，只有所有冻结 Tier 都不能回答题目时才重开 G2。
- 决策分为 A/B/C：A 类改变研究答案或结论范围，冻结后需合并 change request 和用户批准；B 类是数学等价的复现约定，由架构师与实施者冻结前登记；C 类是普通代码缺陷，由实施者直接修复并登记。B 类若改变秩、目标、预测、阈值或模型选择，必须升级为 A 类。
- 未经建模手针对当前版本明确批准，不得把 `model/PLAN_STATUS.txt` 或 `data/PREPROCESSING_STATUS.txt` 改为 `FROZEN`；两者必须同步冻结，本模板升级不等于批准任何具体赛题方案。
- G2 后实现必须遵守冻结方案；数学模型或语义性预处理变化须先写 `model/change-request.md` 并重新获批。
- G2-B 通过后，G3 禁止重新发起无范围的全面方案审计；只有问题触及 A 类、冻结 Tier 无法回退、有最小复现，并且存在非等价歧义或当前唯一 A 类选择被具体失败证明不可执行时才能提出 CR。同一质量门的 A 类问题必须由 `model_architect` 去重合并，一次审批、一次契约更新。
- 实现者不得为自己的结果作最终验收；由 `model_verifier` 独立复现。
- G4 的关键项若为 `FAIL` 或 `NOT_TESTED`，不得通过；`CONDITIONAL` 必须写明论文表述限制。
- G5 只组织有证据的内容；未验证数值不得写成确定性结论。
- G6 Release 前，`reports/late-stage-ai-self-check.csv` 必须覆盖预设 20 项且不存在 `NOT_REVIEWED / ISSUE / NEEDS_CONFIRMATION`；第三方自查表不得冒充官方规则或 AI 作者身份鉴定。
- 只有用户明确要求“打包、压缩、生成快照或发布”时才能执行 G6；禁止定时或自动打包。

## 工程规范

- 保留简单基线并与最终模型使用同一数据划分和指标比较。
- 预测任务的 Tier 必须使用相同外层划分、评价单位和主要指标；非预测任务使用相同场景集、约束口径和评价设计。不得通过换测试集、删除困难样本或更换指标为复杂模型制造优势。
- G2-A 为每个 Tier 登记入口、拟合次数、bootstrap/模拟次数、时间、内存、磁盘、最坏耗时和降级动作。Tier 1 默认不超过可用比赛计算窗口的 40%；Tier 2 运行前至少保留 30% 时间给 G4、制图、论文和故障修复。
- 固定随机种子，记录环境、参数、命令、运行时间、输入哈希和输出位置。
- 正式结果必须由脚本复现，不得只存在于 Notebook 或聊天中。
- 每个题目任务都必须在 `problem/task-requirements.csv` 中映射到模型、实现、检验和论文位置。
- 灵敏度分析须预先说明因素、基准、扰动范围、步长或场景、重复次数、指标、通过阈值和失败动作；不得事后挑选好看的参数区间。
- 稳健性、灵敏度、消融和不确定性分析分别报告，不能相互冒充。
- 保留用户和队友已有修改，不覆盖无关文件。
